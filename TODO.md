# TODO

- [ ] CE-031: Fix `deriveCell` overload order mis-inferring async callbacks
  **Skill:** cause-effect-dev
  **Context:** `deriveCell` (`src/signal.ts:157-164`) declares its function overloads with `MemoCallback<T>` (sync) first and `TaskCallback<T>` (async) second. A zero/single-arg `async () => T` callback is structurally assignable to `MemoCallback<T>` too (fewer params is always fine), and since `MemoCallback` is listed first, TS's overload resolution picks it — unifying `T` to `Promise<...>` instead of the resolved value type. Example: `deriveCell(async () => new Map<string, number>())` infers `Signal<Promise<Map<string, number>>>` instead of `Signal<Map<string, number>>`, which only surfaces when the result is used against an explicit `Signal<T>` annotation elsewhere (e.g. TypeDoc's stricter checking) — plain local `tsc` usage that doesn't cross-check the inferred type won't catch it. The deprecated `createComputed` (same file, `TaskCallback` first at line ~118) intentionally orders `TaskCallback` before `MemoCallback` to dodge exactly this footgun; `deriveCell`'s reordering during the rename reintroduced it. **Fix:** swap the two overload declarations so `TaskCallback<T>` comes before `MemoCallback<T>`, matching `createComputed`'s order. Verified locally: swapping the order resolves `deriveCell(async () => new Map<string, number>())` to `Signal<Map<string, number>>` under `tsc --strict`. Add a regression test (e.g. in the existing overload-resolution test file, if one exists) asserting a zero-arg async callback with no type argument infers the resolved value type, not `Promise<T>`.

- [ ] CE-032: Fix the same overload-order bug in `deriveCollection`/`deriveList`'s per-item forms
  **Skill:** cause-effect-dev
  **Context:** Same root cause as CE-031, found while auditing the codebase for other instances. Four overload pairs declare a single-param sync callback `(sourceValue: T) => R` before the two-param async callback `(sourceValue: T, abort: AbortSignal) => Promise<R>`. Since `R` is unconstrained, a single-arg async callback that ignores `abort` (a common shape) structurally matches the sync overload first, unifying `R` to `Promise<X>` instead of `X`. Locations: `src/nodes/list.ts:110-115` (`MutableList.deriveCollection()`, deprecated), `src/nodes/collection.ts:176-181` (`DerivedList.deriveCollection()`, deprecated), `src/nodes/collection.ts:475-484` (free function `deriveCollection()`, deprecated v1 name), and `src/nodes/collection.ts:838-847` (`deriveList()`'s per-item overloads — **not deprecated, this is the current v2.0-facing API**). Verified via `tsc --strict`: `deriveList(source, async (item) => ({ value: item.id }))` infers `DerivedList<Promise<{ value: string }>>` instead of `DerivedList<{ value: string }>`. **Fix:** swap each pair so the async overload is declared first, same as CE-031. **Not affected (verified, no change needed):** `deriveList`'s whole-array overloads (`collection.ts:826-833`) and `deriveStore` (`store.ts:511-522`) — their sync-form return type is a concrete `T[]`/`UnknownRecord` shape, which blocks the bad unification (a `Promise<X[]>`/`Promise<X>` doesn't structurally satisfy `T[]`/`Record<string, unknown>`, so TS correctly rejects the sync overload for an async callback there). Add regression tests for the four fixed overload pairs, mirroring CE-031's test.

- [ ] CE-033: Backport `Cell`/`MutableCell` types + `isCell`/`isMutableCell` guards to 1.5.2; move Cell-related code to `src/nodes/cell.ts`
  **Skill:** cause-effect-dev
  **Context:** Two related changes bundled together since both touch the same functions. See [ADR-0018](adr/0018-shape-indexed-signal-types.md) § 8 ("1.x bridge: `Cell`/`MutableCell` types and guards") for full rationale.
  1. **File organization:** `src/signal.ts` is reserved for the umbrella `Signal` type and its umbrella-scoped exports (`Signal`, `MutableSignal`, `isSignal`, `isMutableSignal`, `createSignal`, `createMutableSignal`). Move the single-value-shape ("Cell") code — `createCell`, `deriveCell`, `deriveSignal`, `createComputed`, `DeriveCellOptions`, `DeriveSignalOptions`, `isComputed` — into a new `src/nodes/cell.ts`, following the same module pattern as `src/nodes/{state,memo,task,sensor}.ts`. Update internal imports and the public entry point accordingly. No behavior change.
  2. **Type precision:** `deriveCell` currently returns `Signal<T>` (wider than necessary — it can never return a `List`/`Store`/`Collection`). Add `type Cell<T> = State<T> | Memo<T> | Task<T> | Sensor<T>` — each origin already carries a distinct `Symbol.toStringTag` literal, so this union structurally excludes `List`/`Store`/`Collection` (verify none of those satisfy any of the four literal tags). Add `type MutableCell<T> = State<T>` (alias, matching ADR-0018 decision 5: `createCell → MutableCell<T>` aliases `createState`). Update `deriveCell`'s overloads to return `Cell<T>` instead of `Signal<T>`, and `createCell` to return `MutableCell<T>` instead of `State<T>` — both are widening-safe for existing callers (every `Cell`/`MutableCell` value already satisfies `Signal`/`MutableSignal` structurally). Add `isCell(value): value is Cell<T>` (checks `Symbol.toStringTag` membership in `{'State','Memo','Task','Sensor'}`) and the symmetric `isMutableCell(value): value is MutableCell<T>` (equivalent to `isState`, exported under the forward-compatible name). Export `Cell`, `MutableCell`, `isCell`, `isMutableCell` from the package's public entry point.
  Purely additive — no runtime behavior changes, no existing call sites break. Follows the established 1.x v2-bridge precedent (`createCell`/`deriveCell` in 1.5.1).
  **Release vehicle: 1.5.2 (patch), confirmed.** This is not a new capability under REQUIREMENTS.md's "New non-breaking features" bar — the library does nothing it couldn't do before. It rectifies the taxonomy left mis-shaped by the same narrow-`Signal`/wide-`Signal` reversal the 1.5.1 bridge already corrected, so `Cell`/`MutableCell`/`isCell`/`isMutableCell` and the narrowed `deriveCell`/`createCell` return types are forward-compatible groundwork for v2, shipped under the same reasoning and release class as 1.5.1.
