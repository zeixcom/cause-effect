- [x] CE-011: Restore custom composite item factories for `List`'s `createItem` — done, pending review ⏳
  **Skill:** cause-effect-dev
  **Changed:** `src/nodes/list.ts` (`ItemSignalOptions`, `ListOptions`, `List`, `MutableList`, `DeriveListOptions`, `ExternalListOptions`, `listFacade`, `isMutableItem`, `createExternalList`, `deriveList`, `createList`, `isList`, `isMutableList`); `test/list.test.ts`, `test/collection.test.ts`, `test/v2-transition.test.ts`.
  **How:** Loosened `S`'s bound from `Cell<T>`/`MutableCell<T>` back to the umbrella `Signal<T>` / `Signal<T> & { set(value: T): void }` everywhere listed above, keeping every default parameter unchanged at `Cell<T>`/`MutableCell<T>` — so the common (no-`createItem`) case is exactly as tight as CE-003 left it, and only the explicit-`createItem` case regains `Store`/`List` eligibility. Reverted the two CE-003-adapted tests back to `createItem: createStore`, restoring the original nested-Store-field regression coverage and the original custom-factory type-inference assertion.
  **Found and fixed en route:** a single broadened generic signature for `createList` regressed a *different*, ordinary case — `const x: List<T> = createList([...])` (any contextual annotation, no `createItem`) failed to compile, because TS's generic-default resolution picked the loosened bound instead of `MutableCell<T>` when a contextual type was also in play. An overload split (no-`createItem` vs. with-`createItem`) fixed that but broke inference for a bare generic function passed as `createItem` (e.g. `createItem: createStore` without an explicit `<T>`) in the other direction — overload resolution weakens higher-order generic inference in a way a single signature doesn't. Kept the single signature (it's the one that supports bare `createStore` correctly) and instead added an explicit type argument at the one real call site that needed it (`test/v2-transition.test.ts`). Documented the trade-off in `createList`'s JSDoc so a future caller hitting the same contextual-annotation case knows to add `<T>` rather than treating it as a bug.
  **Check:** Confirmed independently reproducible before the fix and clean after: `bunx tsc --noEmit`, `bunx biome check .`, `bun test` (661 pass / 0 fail), `bun run build` all clean; bundle sizes unchanged (index.js 52.56 KB, core gzip 2080B). Worth double-checking whether the same contextual-annotation footgun exists elsewhere in the type surface (e.g. `Store`'s or a future shape's generically-bounded customization points) before it bites a real consumer.
  **Correction (post-review):** the user caught a follow-on imprecision in the first pass — `DeriveListOptions`, `ExternalListOptions`, `createExternalList`, and `deriveList`'s external-push overload all defaulted `S` to `Cell<T>`, but their actual runtime item factory (when `createItem` is omitted) is `createState`, which returns `MutableCell<T>` — a mismatch that in fact predates this task entirely (confirmed present under the old `Signal`-narrow naming before any ADR-0018 Revision work started). Corrected those four defaults to `MutableCell<T>`. Left `List<T,S>`'s own bare default and `isList`'s alone at `Cell<T>` — that one has to stay the loosest covariant bound, since a genuinely read-only List (`deriveList(fn)`, items built from `deriveComputed`) must still satisfy bare `List<T>`/`ListSource<T>`; defaulting it to `MutableCell<T>` would have broken that. Two internal pass-through casts in `deriveList`'s sync/async-derivation branches needed a documented `as unknown as` bridge afterward, since `keyedAdapter`/`derivePerItem` never read `options.createItem` on that path and the value doesn't need to satisfy the now-stricter default. Re-verified clean: `tsc`, `biome`, `bun test` (661/661), `bun run build`.
